# Pulse Console scrcpy 扩展架构（高密度设备集群）

## 目标

scrcpy 是按需启动的交互式视频会话，不是所有设备都持续推流。设备发现、状态监控、批量 ADB 操作必须在没有任何视频会话时也能工作。

## 建议架构

- **Device Registry**：维护 serial、在线状态、型号、IP、最后心跳；状态数据和视频会话状态分离。
- **Session Manager**：每个物理设备最多一个活动 scrcpy 会话；启动/停止幂等；限制全局和单用户并发；闲置超时自动释放。
- **scrcpy Adapter**：封装版本检测、参数生成、子进程启动/停止、退出码和 stderr 日志；不在 HTTP 请求线程中执行长时间启动。
- **Video Gateway**：浏览器通过受认证的 WebSocket/WebRTC 网关观看视频。不要把 scrcpy 原生 TCP 端口直接暴露给 LAN/公网。
- **Task Queue**：启动、停止、重启、ADB 命令以任务方式运行，返回 task/session ID 并可轮询状态。
- **Resource Guard**：对并发视频会话、每设备会话、CPU、内存、文件描述符和网络吞吐设置上限；拒绝超额请求并返回明确错误。
- **Audit & Security**：所有会话控制需认证；随机会话 ID；校验 serial 是否属于已登记设备；停止会话时清理进程及子进程。

## 分级投屏模式

1. **设备墙/概览**：所有设备仅显示状态，不推视频。
2. **缩略图巡检**：只给少量选中的设备低分辨率、低帧率视频；按批轮巡。
3. **多画面监控**：在资源允许的上限内同时看多台设备，默认低分辨率/帧率。
4. **单机交互**：选中一台设备后提升画质，提供键鼠/触摸控制；关闭页面或闲置超时后回收。
5. **批量操作**：优先通过 ADB 执行，不模拟几百个独立的视频输入会话。

## 容量设计原则

不承诺固定“可同时投屏 N 台”，必须在目标机器、分辨率、帧率、编码器、浏览器和网络实测后确定。设备在线数量可远高于活动视频会话数量。

带宽估算公式：
- 总出站带宽（Mbps）≈ 每路实测平均码率（Mbps）× 同时观看路数。
- 例如每路 1.5 Mbps，16 路约 24 Mbps；这只是算术示例，不是性能承诺。
- 编码/解码、转发和浏览器渲染都要分别测量。尽可能避免服务端重复转码；如果必须转码，应单独部署媒体节点并做硬件加速评估。

## 部署分层

- **控制平面**：FastAPI 或现有后端，负责设备清单、权限、任务和会话元数据。
- **设备执行平面**：ADB/scrcpy worker，可与 Web API 分进程运行，防止媒体任务耗尽 API 资源。
- **媒体平面**：按需启动的媒体网关/转发服务。只有在确认 scrcpy 版本、浏览器协议和部署环境后才选择具体网关实现。
- **数据库**：先保留 SQLite（WAL + 索引）用于单实例 MVP；需要多 worker/多控制节点时再迁移 PostgreSQL。
- **队列**：初期可用进程内有界队列；跨进程和多节点部署再引入 Redis 等外部依赖。

## 迭代顺序

1. 盘点仓库已有 ws-scrcpy / live 相关代码与部署方式。
2. 加入只读的 scrcpy 可用性检查、版本与依赖状态 API。
3. 实现单设备会话的 start/status/stop 与资源限制。
4. 打通一个浏览器实时画面和控制闭环，增加鉴权与清理。
5. 加入低带宽缩略图模式、并发限额、空闲超时与队列。
6. 做压力测试：无视频设备数、并发会话数、每路码率、CPU/RAM、断线恢复、长时间稳定性。
7. 根据真实测量逐步提高默认上限。

## 安全底线

- 不要将 ADB server 的 5037 端口或 scrcpy 原生控制端口直接暴露到不可信网络。
- 默认不公开绑定到 0.0.0.0；远程访问应在可信 LAN/VPN 内，并启用认证。
- 对高风险操作（重启、批量操作、安装 APK）增加确认、任务记录和并发限制。
- scrcpy 子进程必须可追踪、可终止，并在服务退出时清理。
